# Lemko Memory Book — Backend

## Run locally (with auto-reload)

One-time setup: create a `.env` file in this directory (git-ignored):

```
DATABASE_URI=postgresql://postgres:postgres@localhost:5432/lemko_memory_book
FLASK_APP=app
FLASK_DEBUG=1
FLASK_RUN_PORT=5001
```

Then start the server:

```bash
./run-local.sh              # auto-reload on code changes (default via FLASK_DEBUG=1)
./run-local.sh --reload     # force auto-reload on
./run-local.sh --no-reload  # run without auto-reload
./run-local.sh --port 5002  # any extra flags are passed through to `flask run`
```

The server runs on http://localhost:5001 and by default **restarts automatically
whenever a backend file changes**. Stop with Ctrl+C.

Health check: `curl http://localhost:5001/hello`

Point the frontend at it via `lemko-memory-book-fe/.env.local`:

```
REACT_APP_API_URL=http://localhost:5001
```

## Settlement data

`settlements`, `settlement_lists`, `settlement_list_settlements` and `families` hold the book's
register of settlements and name lists, and link every family to the list it was read from.
Migrations `0002` and `0003` create and fill them from `migrations/data/*.csv`, so `flask db upgrade`
(run by `startup.sh` on Azure) is all that is needed. The book is the source of truth: values are
stored as printed, nothing is corrected.

The CSVs are generated from the book HTML by the scripts in `../spec/settlements/tools`
(see `../spec/settlements/README.md`); the generator also reads the per-list files of the data
audit in `../spec/data-audit/data`. Regenerate them with:

```bash
cd ..   # the lemko folder
python3 spec/settlements/tools/make_seed_files.py lemko-memory-book-be/migrations/data
```

Migration `0006` brings the list rows of an existing database in line with the regenerated file:
the data audit (`../spec/data-audit`) found that the first seed carried a block's 1944–46 division
too far (110 lists), took 21 headings from parser file names and missed 5 total rows. It also fills
`book_page` (the list's start page as printed in the table of contents) and `list_total_families`
(the family count of the list's own total row, as printed).

The `settlement` string in search and family responses is the heading printed above the
book's list the family was read from (e.g. `Дошниця – Тиханя (від №88)`).

## Area of eviction

`oblasts` (25 destination units with their present-day names) and `areas` (every value of
`area_eviction` as printed, linked to its oblast where the book is unambiguous) come from
migration `0004`, with the data in `migrations/data/oblasts.csv` and `areas.csv`, generated by
`../spec/areas/tools/make_area_seed_files.py`. `evicted_persons.area_id` points at `areas`.
`GET /oblasts` lists the oblasts with people counts; the search takes `oblast=<id>` and returns
an `oblasts` facet. `area=<printed value>` and the `area_evictions` facet remain for the
frontend version before the oblast filter.

Migration `0007` replaces the register values that were the old parser's glued readings of
two-line cells (`Сталінська, ниніДонецька`) with the printed readings, following
`migrations/data/areas_renamed.csv`. Until the data repair rewrites the person rows, the
`area_eviction` text of 118 people still shows the old reading while their `area_id` and the
oblast filter are right.

## Book positions and the data repair

Migration `0005` adds the columns that the data repair planned in
`../spec/data-audit/execution-plan.md` fills; they are empty until it runs:

- `evicted_persons`: `list_id`, `book_tr` (the row's `<tr>` index inside the list's table in the
  book HTML, the row's key), `book_row_no`, `family_position` (book order inside the family),
  `row_kind` (`person`, or `note` for a row the book prints instead of names) and
  `persons_represented`.
- `families`: `printed_no` (the family number as printed: `12`, `138-1`, `4?`), `kind`
  (`numbered`, `individual`, `unnumbered_household`, `unnumbered_group`), `book_seq` and the
  printed `section` the family stands under.
- `family_aliases`: family uuids retired by the regrouping, so old links keep resolving.
- `data_repairs`: log of applied repairs.

The repair itself is `flask repair-book-data`, from `app/commands/repair_book_data.py`. It reads
`migrations/data/repair/` (built by `../spec/data-audit/tools/build_repair_files.py` from the
audit's plan): every printed row with its values as printed and its family, every book entity,
the retired family uuids, and what every list must hold afterwards. It inserts the 7,602 missing
people and 2,594 families, moves 1,116 people to the family the book prints them in, rewrites the
cells that differed from the book, fills the book positions, relinks `area_id`, retires 36
families into aliases and logs itself in `data_repairs`, all in one transaction, and rolls back
unless every check passes. Without `--apply` it is a dry run; `--again` after an apply must
report no changes. It is run deliberately against a database, never from `startup.sh`:

```bash
./venv/bin/flask --app wsgi repair-book-data          # dry run against DATABASE_URI
./venv/bin/flask --app wsgi repair-book-data --apply
```

## Search filters

`GET /search/evicted_persons` takes, besides `query`, `limit` and `offset`:

- `settlement=<settlements.id>`: people whose family the book places in that settlement, or whose
  family's list covers it without naming one village (so Дошниця also returns `Дошниця – Тиханя`).
- `area=<area_eviction>`: exact match on the area of eviction as printed (not normalized).

Filters work without `query`; the 3-character minimum applies to the text only. The response has
facets `last_names`, `area_evictions` and `settlements` (`[{id, name, note, count}]`, top 50 by count),
and each item carries `settlement_id` when the book points at exactly one register entry.

Dropdown data: `GET /settlements` (every register entry with alt names, note, 1939 powiat and people
count) and `GET /search/area_evictions` (every printed value with its count).

## Other commands

```bash
pip install -r requirements.txt      # install dependencies (inside venv)
flask db migrate -m "message"        # generate a migration
flask db upgrade                     # apply migrations
gunicorn wsgi:app                    # production-style run (no reload)
```
